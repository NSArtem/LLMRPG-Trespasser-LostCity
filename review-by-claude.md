# Module structure review

Scope: `module/` on the current branch (`feature/module-extractor-light`), the `module/`
layout `feature/module-extractor` was designed to produce, and the runtime contract in
`chatgpt-project/SETUP_AND_PROMPTS.md` + `MANIFEST.md` that defines what "useful for the
LLM" means here.

Note: there is no `model/` directory; this reads `module/` as the subject. A parallel
review exists in `review-by-codex.md`; findings from it are incorporated below, and the
points where the two reviews disagree are listed in the last section.

## Verdict

The current `module/` is a good extraction artifact and a poor runtime model. The
`feature/module-extractor` design models play far better but is too fragmented to adopt
unchanged. The target is **heavy-branch semantics, light-branch packaging, plus the prompt
integration neither branch has**.

## What each side is

**Current (`feature/module-extractor-light`)** — `module/` is 256 flat cards
(`cards/entities/` 214, `cards/reference/` 42), plus `module.json` (798 KB),
`index.json` (104 KB), `topology.json` (75 KB), `reports/` — about 2 MB total, covering
52 locations, 42 actors, 39 situations, 42 procedures, 39 knowledge records, 19 topology
nodes and 22 passages. A card is generated by
`module-extractor/module_extractor/rendering.py:22` (`_card`), which is fully
type-agnostic: it emits `### <field>` for whatever keys the extraction returned, sorted
alphabetically. `contracts.py:62` requires only `title`+`description` for a location,
`title`+`role` for an actor, `title`+`trigger` for a situation.

**`feature/module-extractor`** — no completed `module/` exists on that branch; it holds
the intended contract as schemas, templates and test fixtures. The intended shape is typed
directories (`places/ situations/ actors/ knowledge/ procedures/ topology/ flow/ audit/
generated/`), every card carrying YAML frontmatter (`id, type, source_refs,
knowledge_level, verification`, and `topology_node` on places), with canonical relations in
graph YAML validated by 10 JSON schemas.

## Evaluating the current module against the runtime prompts

**1. It isn't wired in at all.** `MANIFEST.md` never mentions `module/`. The Project
instructions (`SETUP_AND_PROMPTS.md` §4) say for adventure content: check
`gm/module-overrides.md` and entity files, *then* «PDF приключения». The extracted module
isn't in that chain. Right now its shape is moot — the GM LLM never opens it, and the PDF
stays the default runtime source for every scene, which is expensive and
non-deterministic. The whole point of extraction is to demote the PDF to a **cold audit
source**, consulted only for a missing detail or a suspected extraction error.

**2. The card is a paraphrase index, not something you can run a room from.**
`module/cards/entities/location-area-05-hall-of-guardians.md` in full is a title, four
bullets of metadata, and one `### Description` paragraph. At the table the LLM needs four
things when the party enters: what do they see, what's here, where can they go, what's
hidden. The card answers one. Situations have `trigger` only — `outcome` is present on 9
of 39; `winters-daughter.situation.area-13-sir-chydes-plea.md` is a trigger and one
sentence, which is evidence rather than a runnable encounter. Actors fold stat block,
behaviour, and the ghost's tether-to-the-ring into a single `### Role` blob.

Concretely, the required fields cannot tell the GM: what to present immediately; what
stays secret; what an actor wants, knows, or does in response; what activates an
encounter; what choices the players have; which consequences change world state; whether
something repeats; how a clue is acquired; or whether a statement is true, false, a rumour
or a belief.

**3. Topology is the best data in the module and nothing can reach it.**
`topology.json` has 22 passages with real facets — `kind`, `medium`, `elevation`,
`barriers`, `conditions`, `traversal_direction` ("2-foot-wide rough opening", "requires
crawling", "west door concealed by a tapestry"). But nodes are `area-5` and cards are
`location-area-05-hall-of-guardians`. Verified: **0** topology node IDs appear as record
IDs, and **0** card references point at a topology node. `rendering.py:155` builds an
adjacency list keyed by `area-N` into `index.json`, where nothing can join it. Exits exist
in the data and are absent from every location card, leaving the LLM to infer that
`area-13` means those two location cards — exactly the implicit join that fails under
context pressure.

**4. Three ID namespaces, unreconciled — and the report certifies it clean.** 127 records
use `<type>-<slug>`, 75 use `<type>.<slug>`, 54 use `winters-daughter.<type>.<slug>`.
Exact type+title matching finds 19 duplicate groups covering 39 records, and that is a
**floor**, not a count: it misses same-entity-different-title cases such as
`actor-sir-chyde` / `actor-ghost-of-sir-chyde` / `winters-daughter.actor.area-13-sir-chyde`
(three records, one NPC). Other overlaps: `item-ring-of-soul-binding` /
`item.ring-of-soul-binding`; `effect-ring-of-soul-binding` / `effect.ring.binding`;
duplicated locations across areas 3–14. There are 52 location records for a 19-node map.

The duplicates are complementary rather than redundant — `location-area-13-knights-tomb`
comes from page 19 prose, `winters-daughter.location.area-13-the-knights-tomb` from the
page 29 map — so an LLM loading either one misses half the room.
`reports/conflicts-and-gaps.md` reports "0 conflicts" because reconciliation compares
observations *within* an ID and never detects that two IDs describe the same thing;
`index.json.aliases` is empty. This is worse than a gap: the audit certifies a
contradiction as clean.

**5. No `knowledge_level`, no frontmatter.** The Project instructions carry a hard rule —
«Соблюдай knowledge_level. Не раскрывай gm/ игроку напрямую». Every campaign-side
template has `knowledge_level` in frontmatter. No module card has any frontmatter. So the
LLM cannot tell whether "the ghost is tethered to the ring and cannot exist more than 10
feet from it" is boxed text or a GM secret — and that card mixes both.

**6. No join to the mutability contract.** Per §4 of the prompts, the module is
«исходное состояние модуля до изменений кампании» and campaign state overrides it. But
`gm/module-overrides.md` keys its table on free-text «Объект / место», not on a module
record ID. There is no deterministic way to ask "is area 5 still as written?" — and no
runtime step that says "apply overrides" can be executed reliably until there is.

**7. Wrong loading granularity.** The prompt's load rule is «только релевантные сцене
NPC, локации» — the unit is the *scene*. The module's unit is the *record*, and neither
the cards nor `index.json` answer the actual runtime question: *given the current
location, what exact bundle should I load?* Running one room means opening the location
card, four referenced cards, and `topology.json`, and even then getting no exits.
`index.json` is already 104 KB for a 31-page adventure because every record inlines
`source_pages` and every topology entry inlines observations.

**8. Audit and runtime representations are mixed.** `module.json` (798 KB) carries raw
observations, confidence, packs, coverage, conflicts, review hashes and release-gate data.
That is valuable for extraction auditing and useless as GM context, and it sits in the
same tree a GM LLM might glob.

## What `feature/module-extractor` got right

| Concern | Current | Heavy branch |
| --- | --- | --- |
| Locations | title + description | impression, occupants, triggers, hazards, resources, exits, `topology_node` |
| Actors | title + role | goals, resources, knowledge, reactions, source mechanics |
| Situations | trigger, sometimes outcome | activation, location, participants, pressure, decisions, outcomes, completion, repeat |
| Knowledge | undifferentiated text | fact/clue/rumour, truth status, acquisition, discoverability, reveals/contradicts |
| Procedures | trigger + prose steps | schedules, transitions, stop/reset conditions, source mechanics |
| Topology | nodes + passages, unlinked | typed edges with state, requirements, hazards, direction; linked from places |
| Secrecy | none | `knowledge_level` on every card |
| Runtime loading | not integrated | place → topology slice → situation bundle |
| Campaign changes | overrides only | immutable baseline + typed topology overlay + overrides |

Its four structurally correct calls:

- **Frontmatter typing on every card** — `id, type, source_refs, knowledge_level,
  verification`. Gives the runtime the secrecy signal and the provenance without spending
  prose on it.
- **`topology_node` + a `## Выходы` section listing edge IDs** on the place card. The
  card↔map join the light version is missing.
- **Prose and canonical state separated by role.** The situation card holds «Назначение /
  Предъявление игрокам / Тактика ведения» — improvisation guidance — while
  `flow/situation-flow.yaml` owns `activation`, `participants`, `decisions`,
  `outcome_refs`, `completion_conditions`, `repeat`. Prose for the narration, structure
  for the state.
- **Knowledge as a typed graph** — `kind: fact|clue|rumor`, `truth_status`,
  `available_from`, `discoverable_at`, `acquisition`, `reveals`/`contradicts` — in the
  same vocabulary the checkpoint format already speaks (`new_facts.kind:
  established|npc-claim|rumor|belief`, `truth_status: confirmed|unverified|false|mixed`,
  `knowledge_changes.knowledge_ref`). Light's `knowledge` card is `title` + one text blob
  and throws all of it away.

And one mechanism worth lifting wholesale: **the campaign topology overlay**
(`schemas/topology-overlay.schema.json`, `templates/campaign/topology-overlay.yaml`). It
keeps `module/topology` immutable and expresses route changes as typed deltas —
`operation` from a closed set (`set_state`, `collapse`, `block_temporarily`,
`reveal_secret`, `remove_edge`, …) with `target`, `checkpoint_id: cp-NNNN`,
`source_event: event-NNN`, `reason`, and `knowledge_subjects`. That is already the
checkpoint contract's vocabulary, applied to the map. It solves mutable route state
without making the module mutable, and it is the model the rest of the module should
follow.

**Where the heavy design goes too far:** every situation exists as a card *and* a YAML
entry under two different IDs joined by `situation_ref` — two files, two IDs, one concept,
and the runtime must load both to answer anything. Operational data is split across cards,
topology YAML, flow YAML, knowledge YAML, procedure YAML, source indexes and audit files,
so running one encounter takes several joins. Mandatory geometry, measurements, typed
links and verification fields force `unknown` values through ordinary adventure prose.
`generated/` treats renderings as first-class content. That cost is what made hand
authoring infeasible, and it would hurt runtime loading too.

## Recommended structure

Keep light's generation model (deterministic assembly from bounded evidence — that lesson
holds), adopt heavy's typing, and fix the granularity both got wrong. **Make the location
the loading unit and make it self-sufficient**; carry relations in frontmatter so one file
serves both the narration and the state machine.

```
module/
  MODULE.md          # ~2 KB: system, level range, premise, area list, how to use
  index.json         # id → {type, title, path, area, typed refs}; no provenance inline
  cards/
    places/          # THE loading unit — one file per keyed area
    actors/
    situations/
    knowledge/
    procedures/
    reference/       # rules, items, tables, effects
  topology.yaml      # build-time source of truth; denormalized into place cards
  audit/             # coverage, conflicts, review, provenance — never loaded at play time
```

Place card:

```markdown
---
id: place.winters-daughter.area-13
type: place
title: The Knight's Tomb
topology_node: area-13
source_pages: [19, 29]
exits:
  - to: area-12
    via: corridor
    initial_state: open
    barrier: null
    knowledge_level: player-visible
  - to: area-14
    via: concealed door
    initial_state: closed
    barrier: "hidden behind the tapestry"
    knowledge_level: gm-secret
refs:
  situations: [situation.winters-daughter.sir-chyde-plea]
  actors:     [actor.winters-daughter.sir-chyde]
  knowledge:  [knowledge.winters-daughter.tomb-goods]
  procedures: []
---
## First impression   <- player-safe, narratable as written
## Features
## Occupants
## Triggers
## Hazards
## Resources
## Exits              <- prose gloss on the frontmatter
## GM secrets         <- GM ONLY; what action reveals each item
```

Situation card — structured activation and GM prose in **one** file, avoiding the heavy
branch's split identity:

```markdown
---
id: situation.winters-daughter.sir-chyde-plea
type: situation
location_refs: [place.winters-daughter.area-13]
participants:  [actor.winters-daughter.sir-chyde]
activation: enter_place
repeat: once
outcomes:
  - id: accept-request
    effects:
      - operation: add
        target: open_thread.recover-ring
---
## What the players perceive
## Pressure and stakes
## Likely approaches
## Actor reactions
## Consequences
## Completion conditions
```

### The changes that carry the value

1. **Join topology into the place card at render time.** The facet data already exists;
   `rendering.py` just doesn't join it. Requires reconciling `area-N` against the card
   namespace first.
2. **Split every card into a player-safe part and a GM-only part.** One `knowledge_level`
   per file is not enough — the ghost card needs both. This is the prompts' hardest
   requirement and the current format cannot express it.
3. **Collapse the three ID namespaces to one and merge duplicates** (not alias them —
   the pairs are complementary, so an alias map still forces two loads). Add
   near-duplicate detection to reconciliation so `conflicts-and-gaps.md` stops reporting 0
   on 52 locations over a 19-node map.
4. **Make module IDs the join key in `gm/module-overrides.md`** — add an ID column. Then
   module = immutable base, override table = diff, and "is this still as written?" becomes
   a deterministic lookup rather than a text match.
5. **Adopt the topology-overlay pattern for all campaign deltas**, and make module IDs
   directly usable in checkpoint packages: module `knowledge.*` IDs as
   `knowledge_changes.knowledge_ref`, situation outcomes as `changes` entries
   (`operation`/`target`/`from`/`to`). The overlay schema already proves the pattern
   works; extend it past topology.
6. **Move provenance out of the runtime path.** `source_pages` stay on the card;
   observations, pack IDs, confidence, coverage and review hashes go to `audit/`.
7. **Wire `module/` into `MANIFEST.md` and the Project prompt.** Without this the rest is
   inert.

## Prompt-loading contract

`MANIFEST.md` and `SETUP_AND_PROMPTS.md` §4 need an explicit algorithm:

1. Read `CURRENT.md` and the active campaign files.
2. Resolve the scene's `module_ref` to a place card.
3. Load that place card.
4. Load its `refs` — active situations, present actors — and the knowledge and procedures
   those situations reference. Nothing else.
5. For movement, use the place card's `exits`; open `topology.yaml` only for multi-hop
   route questions.
6. Apply `gm/module-overrides.md` and the campaign topology overlay by module ID; the
   overlay wins over the card's `initial_state`.
7. Never narrate from a `## GM secrets` section or a `knowledge_level: gm-secret` exit.
8. Consult the adventure PDF only for a detail the module lacks, a suspected extraction
   error, or an audit — never as default scene context.

Precedence for adventure content becomes: `gm/module-overrides.md` + topology overlay →
`module/cards/**` → PDF.

## Open decision

Module cards are currently English (source-faithful) while every campaign-side file is
Russian, and the heavy branch's templates were Russian with TODOs. Keeping extraction
English and letting the GM LLM translate at narration time is the cheaper default — but if
`## First impression` should be narratable verbatim, that is a change to the extraction
contract, not the renderer. Settle it before rewriting `rendering.py`.

## Divergences from `review-by-codex.md`

Both reviews agree on every diagnosis above and on "heavy semantics + light packaging".
They differ on the target design, along one axis — how much normalization the runtime can
afford:

- **Exits.** `review-by-codex.md` keeps them in `topology.yaml` and links via
  `topology_node`. That preserves the join it criticises in its own §4; this review
  denormalizes exits into the place card and treats the graph as a build input.
- **`active_situations` in the index.** Which situations are active is campaign state, not
  module baseline; putting it in the module index contradicts the immutable-baseline
  principle both reviews adopt.
- **`load_with`.** Real need, but it is the existing `references` list with types
  attached, not a second mechanism that can drift from the first — hence `refs:` above.
- **File-level `knowledge_level: gm-secret` on a place card** that also has a
  `## First impression`. Those cannot both hold; secrecy has to be per-section.
- **"Merge or alias" duplicates.** Alias is the weaker branch and shouldn't be offered as
  equivalent, because the duplicate pairs are complementary.
- **Generated Mermaid views.** Codex dismisses them with SVG; a compact text map is one of
  the more useful artifacts for a text model, and worth keeping.
